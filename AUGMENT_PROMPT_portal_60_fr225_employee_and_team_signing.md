# Portal 60 — FR.225: Fix Org Employee Rows + Audit Team Signing

## Context

Two things are broken in FR.225 Opening/Closing Meeting Form viewer after Portal 59:

1. **Org employee rows show `[SIG:ORG_OPENING_ORG_EMP_BLANK_0]` even when the client
   has registered employees.** This means `_resolve_org_attendees()` returned an empty
   list at FR.225 generation time — either because the `client_org_employees` table
   was missing (silent exception), or because the package was generated before employees
   were registered. Employees added after the package download don't appear.

2. **Audit team slots (`[SIG:ORG_OPENING_LEAD_AUDITOR]` etc.) are not clickable even
   when the Lead Auditor is logged in.** The `ORG_TEAM_RE` eligibility check in
   Portal 59 requires `current_user.auditor_id == stage.lead_auditor_id`. If either
   field is NULL or the frontend doesn't render a clickable button for `current_user`
   status on these key prefixes, signing is impossible.

        ).first()
        if not client:
            logger.warning("[FR225] No client user found for audit_set_id=%s", audit_set.id)
            return _blank_placeholder_rows()
        
        employees = (
            db.query(ClientOrgEmployee)

            .order_by(ClientOrgEmployee.created_at)
            .all()
        )
        logger.info("[FR225] Found %d employees for client_id=%s (audit_set=%s)",
                    len(employees), client.id, audit_set.id)
        
        if not employees:
            logger.warning("[FR225] Zero employees found — using blank placeholders")
            return _blank_placeholder_rows()
        
        return [
            {"name": e.full_name, "role": e.role_title, "sig_key": e.id}
            for e in employees
        ]
    except Exception as ex:
        logger.error("[FR225] _resolve_org_attendees error: %s", ex, exc_info=True)
        return _blank_placeholder_rows()

    return [{"name": "", "role": "", "sig_key": f"ORG_EMP_BLANK_{i}"} for i in range(3)]

## Fix 1 — FR.225 re-generation endpoint (fixes timing problem)

The core issue: FR.225 is generated by the packager at audit package download time.
If the client registers employees after the auditor downloads the package, the DOCX
already exists in storage with blank rows. The fix is a dedicated endpoint that
regenerates FR.225 using the current employee roster and replaces the stored document.

**File:** `backend/audit_set/documents_router.py`

Add endpoint:
```python
@router.post("/{audit_set_id}/meeting-form/regenerate")
def regenerate_meeting_form(
    audit_set_id: str,
    stage_type: str,       # "stage_1" or "stage_2"
    db: Session = Depends(get_db),
    current_user: PlatformUser = Depends(require_any),
):
    """
    Regenerate FR.225 for this audit set / stage using the current org employee roster.
    Call this after the client registers employees, before signing begins.
    Only auditors/planners/admins can trigger this.
    """
    audit_set = db.query(AuditSet).filter_by(id=audit_set_id).first()
    if not audit_set:
        raise HTTPException(404, "Audit set not found")
    
    # Delete existing meeting_form document for this stage (if any)
    existing = (
        db.query(AuditDocument)
        .filter_by(
            audit_set_id=audit_set_id,
            document_type="meeting_form",
            stage_type=stage_type,
        )
        .first()
    )
    if existing:
        # Delete associated VSP records so the viewer re-scans after regeneration
        db.query(VisualSignaturePlacement).filter_by(document_id=existing.id).delete()
        db.query(AuditDocumentSignature).filter_by(document_id=existing.id).delete()
        db.query(DocumentSignatureField).filter_by(document_id=existing.id).delete()
        db.delete(existing)
        db.flush()
    
    # Re-run the packager for FR.225 only
    doc = _generate_meeting_form(db, audit_set, stage_type)  # see below
    db.add(doc)
    db.commit()
    return {"id": doc.id, "message": "FR.225 regenerated with current employee roster"}
```

**`_generate_meeting_form(db, audit_set, stage_type)` helper:**

This should call the same logic the packager uses for FR.225:
- Load stage context (dates, auditor names, standards etc.)
- Call `_resolve_org_attendees(db, audit_set)` — now gets CURRENT employees
- Run docxtpl on the FR.225 template
- Convert DOCX → PDF via LibreOffice
- Create and return an `AuditDocument` record

If the packager already has a single function that generates one document type, extract
FR.225 generation into a reusable helper. If not, write the helper inline calling
`packager.generate_document("meeting_form", stage_type, audit_set, db)` or equivalent.

**Frontend — add "Refresh FR.225" button:**

In the auditor's stage view (wherever FR.225 is uploaded/shown), add a button:
```
[↺ Refresh meeting form with current attendees]
```
This calls `POST /audit-sets/{id}/meeting-form/regenerate?stage_type=stage_1` and
refreshes the document viewer. Show the button only when role is auditor/planner/admin.

## Fix 2 — `ORG_EMP_BLANK_*` rows: make them non-interactive

Blank placeholder rows (`sig_key = "ORG_EMP_BLANK_0"` etc.) generate markers like
`[SIG:ORG_OPENING_ORG_EMP_BLANK_0]` in the PDF which pdfplumber detects but the
viewer can't route to any signer. They show as dead text in the viewer.

**File:** `backend/audit_set/viewer_router.py`

In `_get_field_status`, in the `ORG_EMP_RE` branch (where it matches
`ORG_OPENING_ORG_EMP_*`), add a guard for the BLANK placeholders:

```python
m = ORG_EMP_RE.match(sig_key)
if m:
    emp_id = m.group(2)  # the UUID part
    
    # Blank placeholder rows — not signable, show as informational
    if emp_id.startswith("BLANK_"):
        return _result("pending", label="Awaiting employee registration")
    
    # ... rest of existing ORG_EMP logic
```

This gives blank rows a clean "pending" label instead of a broken state.

Also in `_assert_can_sign` — ensure BLANK keys are rejected:
```python
if emp_id.startswith("BLANK_"):
    raise HTTPException(400, "This row is a placeholder — register employees first")
```

## Fix 4 — Ensure `PlatformUser.auditor_id` is set for auditor accounts

The `ORG_TEAM_RE` eligibility check uses `current_user.auditor_id`. This field is
set via the Portal 48 "Link auditor profile" flow in Admin → Users. If an auditor
account was created but never linked to an `Auditor` profile record, this field is NULL.

**Check on Railway:**
```sql
SELECT id, email, role, auditor_id 
FROM platform_users 
WHERE role = 'auditor';
```

If any auditor has `auditor_id IS NULL`, go to Admin → Users → that user → "Link to
auditor profile" and select the matching auditor.

If the Portal 48 linking UI is not working, or the link isn't being saved:

**File:** wherever the "link auditor" action is handled in the backend (probably
`admin_router.py` or `user_router.py`). Ensure `PATCH /admin/users/{id}` accepts
`auditor_id` and saves it to `PlatformUser.auditor_id`.

for `ORG_OPENING_*` / `ORG_CLOSING_*` key prefixes

**File:** wherever the viewer renders signature overlay buttons
(probably `SignatureOverlay.tsx` or `DocumentViewer.tsx`).

The viewer receives a list of sig fields with their status. For each field, if
`status === "current_user"`, it should render a clickable button. Check whether
there's any filtering that restricts clickable buttons to a known list of key prefixes
(like `ORG_REP`, `LEAD_AUDITOR`, etc.) and excludes new prefixes like `ORG_OPENING_*`.
